# Noctalia v5 adapter

[noctalia.nix](noctalia.nix) wraps the pinned native Noctalia v5 application.
The upstream `noctalia-shell` wrapper targets v4 JSON files and different
environment variables, so its copying/settings options are not compatible.

Use `flake.wrappers.noctalia.wrap` with `settings`, `configHome`, and `stateHome`.
The location options have the native XDG home-root shape: Noctalia appends
`/noctalia`. Defaults are `${XDG_CONFIG_HOME}` and `${XDG_STATE_HOME}`;
unset XDG variables receive their standard HOME fallbacks. These options set
the Noctalia-specific environment without redirecting apps' XDG directories.
`sync.defaultDir` follows `configHome` inside the adapter.

There is one declared `settings` baseline and one exported baseline:

| Runtime file | Sync policy | Sources |
| --- | --- | --- |
| `configHome/noctalia/config.toml` | `replace` | Saved snapshot, then explicit settings |
| `stateHome/noctalia/settings.toml` | `merge` | The same ordered sources |

`constructFiles` mirrors the native `noctalia/config.toml` and
`noctalia/settings.toml` paths. Settings uses a different destination directory
because Noctalia stores GUI overrides under its state root. Its sources reuse
the config entry's complete baseline, including automatic snapshot imports.

On eligible launches, config-only edits disappear and conflicting settings
values reset to the baseline. Settings-only keys survive; merge does not delete
undeclared keys. GUI changes can override the baseline during the session.
Noctalia removes redundant overrides itself when saving values that match its
lower config layer. Sync does not emulate that compaction.

Automatic sync runs on shell launch (no arguments, `-d` or `--daemon`). IPC,
config inspection/validation, theme generation and other client commands do not
sync. Run `noctalia-sync` explicitly to initialize or reapply the baseline before
using `noctalia config validate` in a fresh profile. The standard per-file sync
triggers remain available. There are no reset scripts, snapshot hooks or sync
services in this adapter.

`noctalia-snapshot` reads runtime config first and optional settings second:
settings wins conflicts, tables merge recursively, and arrays replace whole.
It exports only `noctalia/config.toml` under `snapshot.defaultDir`. Missing/empty
settings retains the config layer; malformed settings fails capture and preserves
the previous export. Snapshot never syncs first. Explicit declarations win when
that captured baseline is imported on the next build.

This is a two-file master-config adapter. Native additional root TOML files and
includes still load, but their contents are not flattened into the snapshot.
Keep reusable baseline preferences in `settings` or the captured master file.
The native internal `state.toml`, caches and credential stores are never sources.

## Snapshot review

Pruning applies after combining the two sources, to both layers equally. A
rejected override is omitted; it does not resurrect the older config value.
This deliberately replaces the previous feature's custom prune-before-merge
algorithm with the standard sync-snap pipeline.

Retained categories include theme selection, template IDs, plugin choices,
ordinary widget/bar preferences, audio, notifications, idle behavior and shell
preferences. Defaults remove config-version bookkeeping, widget layouts with
instance references, hooks/includes, storage wiring, calendar accounts, UI scale,
monitor/device selectors, locations, local file paths and credential-like keys.
Store paths are regenerated by the feature. Pruning inside an array drops the
entire array, preserving positional/reference integrity; empty tables are removed.
Plugin-specific fields may need feature-specific pruning; arbitrary third-party
plugin settings are not a schema-validated secret store.

The [checks](checks/check.nix) use independent fixtures and the real Noctalia
`config validate`/`config export` commands to verify precedence and restored
preferences. A fake launch executable checks automatic sync and argument handling
without starting a desktop. Synthetic private fields test pruning, including
both input layers and excluded `state.toml`. Each test finishes by capturing and
comparing the retained baseline. These are CLI/filesystem tests, not GUI save or
live desktop tests.

Reference: [Noctalia configuration](https://docs.noctalia.dev/noctalia/configuration/).
The pinned source includes the full version-matched guide under
`docs/user/configuration/index.mdx`.

The configured feature's manual snapshot command was also run against an isolated
profile and reviewed: 12 preference sections remained, including Gruvbox,
plugin/template selections and widget configuration. Wallpaper store paths and
feature-specific host selection were absent. Native validation passed with
warnings for plugins not installed in the isolated profile; plugin downloads,
sign-in and GUI interaction were not tested.
